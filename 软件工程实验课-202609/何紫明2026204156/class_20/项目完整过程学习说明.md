# 项目完整过程学习说明

这份文档是为了帮助你从“做题式编码”转向“软件工程思维”，理解一个小型命令行项目从需求到实现、测试、文档和维护的完整过程。它不是简单的代码说明，而是从软件工程角度来分析整个项目。

---

****## 1. 项目目标：我们在做什么？

这个项目的目标是：

- 实现一个简单的命令行待办事项管理系统；
- 支持用户添加任务、查看任务、完成任务、删除任务；
- 让任务数据在程序退出后仍然保留，不会丢失；
- 通过命令行界面完成增删改查功能。

从工程角度看，这个项目用来训练的是以下能力：

1. 需求分析能力
2. 模块设计能力
3. C 语言程序结构设计能力
4. 文件读写与数据持久化能力
5. 命令行交互设计能力
6. 测试与文档编写能力
7. 软件工程中“完整闭环”的思维

## 2. 从需求到实现：完整过程

### 2.1 需求确认

项目最开始不是直接写代码，而是先确认“系统应该做什么”。

从题目中我们可以得到这些需求：

- 用户可以添加任务
- 任务要有编号
- 用户可以查看所有任务
- 用户可以完成某个任务
- 用户可以删除某个任务
- 程序退出后，任务不能丢失

这一步很重要，因为它决定了后面的设计和实现方向。

如果需求不明确，代码就会不断修改，最终变成一团乱麻。

### 2.2 需求拆解

我们把需求拆成多个功能点：

- 添加任务：`add`
- 查看任务：`list`
- 完成任务：`done`
- 删除任务：`delete`
- 保存数据：写入文件
- 读取数据：从文件在启动时加载

这就是软件工程中的“需求拆分”，也叫功能拆解。大的任务被拆成几个独立的小功能，每个小功能都更容易实现和测试。

## 3. 设计阶段：怎么组织代码？

写代码之前，最需要考虑的是：

- 数据结构怎么存储？
- 程序怎么分层？
- 哪些函数负责什么职责？
- 程序如何运行？

### 3.1 数据结构设计

项目中核心数据结构是：

```c
typedef struct {
    int id;
    char content[MAX_CONTENT_LEN];
    int done;
} Task;

typedef struct {
    Task tasks[MAX_TASKS];
    int count;
} TaskList;
```

这里有两个结构：

- `Task`：表示一个任务

  - `id`：任务编号
  - `content`：任务内容
  - `done`：是否已完成
- `TaskList`：表示全部任务列表

  - `tasks[]`：任务数组
  - `count`：当前任务数

为什么这样设计？

因为程序需要在内存中维护许多任务，数组最简单直接，且适合这个小型项目。

这是软件工程中的“数据建模”：先决定数据怎么表示，再决定功能怎么处理这些数据。

### 3.2 程序功能模块设计

本项目的核心功能模块可以理解为：

1. `main()`：程序入口，负责接受命令
2. `load_tasks()`：启动时读取文件中的任务
3. `save_tasks()`：退出或操作后写回文件
4. `add_task()`：新增任务
5. `list_tasks()`：展示任务列表
6. `mark_done()`：标记已完成
7. `delete_task()`：删除任务
8. `handle_command()`：分发命令

这种设计符合软件工程中的一个重要原则：

“一个函数只做一件事。”

不是把所有逻辑都塞进 `main()`，而是把功能拆分为多个函数，结构更清晰，后续维护更方便。

## 4. 实现阶段：代码是怎么写的？

### 4.1 命令行入口设计

程序的入口是：

```c
int main(int argc, char *argv[])
```

这里 `argc` 和 `argv` 是标准的命令行参数参数。

- `argc`：参数个数
- `argv`：参数内容

比如：

```bash
./todo add "学习C语言"
```

会被解析成：

- `argv[0]` = "./todo"
- `argv[1]` = "add"
- `argv[2]` = "学习C语言"

这说明系统可以识别命令，并根据第一个参数决定执行什么功能。

### 4.2 命令处理逻辑

项目中通过 `handle_command()` 分发命令：

```c
if (strcmp(command, "add") == 0) {
    ...
}
else if (strcmp(command, "list") == 0) {
    ...
}
else if (strcmp(command, "done") == 0) {
    ...
}
else if (strcmp(command, "delete") == 0) {
    ...
}
```

这里体现了软件工程中的“分支处理”思想：

- 先识别用户的命令；
- 再执行对应处理逻辑；
- 其他情况给出错误提示。

这类似项目中常见的控制器或路由设计。

### 4.3 任务编号管理

任务编号的生成逻辑是：

```c
task.id = list->count == 0 ? 1 : list->tasks[list->count - 1].id + 1;
```

也就是说：

- 第一个任务编号是 1；
- 后续任务编号自动递增。

这样的设计保证编号唯一，并且方便用户通过编号完成操作。

### 4.4 任务删除后的编号重排

删除任务时，代码不是简单地把数组某个位置置空，而是做了整体前移：

```c
for (int i = index; i < list->count - 1; i++) {
    list->tasks[i] = list->tasks[i + 1];
}
list->count--;

for (int i = 0; i < list->count; i++) {
    list->tasks[i].id = i + 1;
}
```

这一步很关键：

- 删除后任务会被重新压缩；
- 编号会重新连续；
- 用户界面不会出现“1,3,4”这种不连续编号。

这个细节体现了程序设计时对用户体验的思考。

## 5. 数据持久化：为什么任务不会丢失？

这是这个项目最值得学习的部分之一。

### 5.1 为什么需要持久化？

如果程序只把任务存在内存中，那程序一退出，任务就消失了。

这不符合待办事项管理系统的基本要求。

所以我们需要把任务写到文件中，程序下一次启动时再加载回来。

### 5.2 文件格式设计

任务保存的格式是：

```text
1|学习C语言|0
2|复习数据结构|1
```

每一行表示一个任务，结构是：

- 任务编号
- 任务内容
- 是否完成

中间用 `|` 分开，这是典型的文本数据存储格式。

### 5.3 文件存储逻辑

```c
int save_tasks(const TaskList *list, const char *path) {
    FILE *fp = fopen(path, "w");
    ...
    fprintf(fp, "%d|%s|%d\n", list->tasks[i].id, list->tasks[i].content, list->tasks[i].done);
}
```

`fopen(..., "w")` 表示写文件，覆盖原文件内容。

```c
int load_tasks(TaskList *list, const char *path) {
    FILE *fp = fopen(path, "r");
    ...
    while (fgets(line, sizeof(line), fp) != NULL) {
        ...
    }
}
```

`fopen(..., "r")` 表示读取文件。

### 5.4 为什么这是软件工程的重要能力？

因为很多真实项目都不是“纯内存程序”，而是需要：

- 数据保存
- 配置管理
- 用户状态恢复
- 文件日志
- 数据备份

持久化就是程序从“临时工具”走向“可用系统”的关键一步。

## 6. 交互模式：为什么程序既能命令行运行，也能交互运行？

项目设计了两种使用方式：

### 方式 1：直接命令执行

```bash
./todo add "学习C语言"
./todo list
./todo done 1
./todo delete 2
```

适合脚本、自动化、快速使用。

### 方式 2：交互模式

```bash
./todo
```

然后用户输入：

```text
todo> add 学习C语言
todo> list
todo> done 1
todo> quit
```

这是一个很典型的软件工程设计：

- 命令行接口（CLI）
- 交互式界面

项目中通过循环读取用户输入：

```c
while (1) {
    printf("todo> ");
    if (fgets(input, sizeof(input), stdin) == NULL) {
        break;
    }
    ...
}
```

这个设计非常适合学习，因为它体现了：

- 程序流程控制
- 输入处理
- 用户友好提示
- 循环结构

## 7. 错误处理：什么叫工程思维？

很多新手写代码时，最容易忽略的是“错误处理”。

本项目中有很多错误场景：

- add 但没有内容
- done 时 ID 不存在
- delete 时 ID 不存在
- 文件无法写入
- 程序解析命令失败

代码中通过 `fprintf(stderr, ...)` 输出错误信息，并返回非零值：

```c
fprintf(stderr, "未找到任务 ID=%d。\n", id);
return 1;
```

为什么这是重要的？

因为一个好的软件不是“能跑”，而是：

- 在正确输入时正常工作；
- 在错误输入时给出合理反馈；
- 避免出现崩溃、异常、无提示等情况。

这也是工程设计中非常关键的一部分。

## 8. 代码中的软件工程思想

这一部分非常关键，你需要从“代码会运行”升级到“代码为什么这样写”。

### 8.1 模块化

把功能拆成多个函数，不把所有逻辑塞在一个地方。

好处：

- 便于调试
- 便于复用
- 便于扩展
- 便于团队协作

### 8.2 数据结构驱动开发

先定义 `Task` 和 `TaskList`，再写函数处理它们。

这是经典的软件工程方法：

- 先抽象数据
- 再设计行为

### 8.3 分层思维

项目中实际上有几层：

- 用户输入层：命令参数和交互输入
- 业务逻辑层：添加、删除、完成任务
- 数据层：文件存储和读取
- 展示层：输出任务列表和状态

这是一个非常基础但很重要的工程思维：

“让每一层负责自己的事情。”

### 8.4 可维护性

如果以后需要支持：

- 优先级
- 分类
- 完成时间
- 任务排序
- 多用户

那么就不需要重写整个程序，而是直接扩展现有模块。

这就是软件工程中最重要的设计目标之一：

“让未来的改动尽可能小。”

## 9. 测试是如何进行的？

在工程中，写完代码后不能直接结束，而是要测试。

### 9.1 功能测试

例如：

- 添加任务
- 列出任务
- 完成任务
- 删除任务

这些测试验证核心功能是否正常。

### 9.2 边界测试

例如：

- 删除不存在的任务
- 完成不存在的任务
- 输入空字符串
- 空列表查看

边界测试可以发现很多隐藏问题。

### 9.3 持久化测试

关键验证：

- 任务添加后退出程序
- 再次启动程序
- 是否仍然存在

这个测试验证了项目的“系统能力”而不是只“单次运行能用”。

## 12. 你怎么学得更透彻？

如果你真的想“学懂”这个项目，不要只看代码结果，而要按下面顺序思考：

### 第一步：看需求

问自己：

- 这个系统最核心的目标是什么？
- 用户有哪些操作？
- 哪些行为是必须的？

### 第二步：看数据结构

问自己：

- 为什么用 `Task` 和 `TaskList`？
- 任务内容为什么要保存到结构体中？
- 为什么要存 `done` 状态？

### 第三步：看函数职责

问自己：

- `add_task()` 做了什么？
- `list_tasks()` 怎么输出？
- `save_tasks()` 和 `load_tasks()` 为什么要分开？

### 第四步：看工程设计

问自己：

- 为什么不把所有代码塞到 `main()` 中？
- 代码为什么分层？
- 为什么需要误差处理？

### 第五步：看测试

问自己：

- 哪些情况属于正常功能？
- 哪些情况属于边界情况？
- 程序是否真的满足需求？

### 第六步：看扩展

问自己：

- 如果我要加“优先级”，应该在哪个函数改？
- 如果我要加“分类”，需要修改哪些结构？
- 如果我要做一个 GUI 版本，如何复用这些逻辑？

这一步正是工程思维开始成熟的标志：

不是“代码能跑”，而是“代码容易扩展”。
